# Sign In

Sign In 是独立的插件化任务自动执行程序，提供任务管理、插件市场、定时执行、执行记录、指标、代理和通知。支持 Linux amd64、arm64，以单镜像、单容器方式部署。

使用前需要有效授权码。主程序不捆绑插件，首次使用后从可信插件源安装所需插件。

## Docker Compose 安装

```yaml
services:
  app:
    image: dingding229/sign-in:latest
    ports:
      - "8000:8000"
    volumes:
      - ./data:/data
    environment:
      TZ: Asia/Shanghai
      # 可选：也可以首次打开网页后输入授权码
      # AUTHGO_LICENSE: "你的授权码"
    restart: unless-stopped
    stop_grace_period: 35s
```

```sh
docker compose up -d
```

打开 `http://服务器地址:8000`。对公网部署时请配置 HTTPS，避免授权码、密码或会话凭证被窃取。不要将数据目录放在公开网站目录中。

## 首次使用

1. 准备空的 `data/` 目录。程序不支持沿用其他版本或开发期间生成的数据。数据目录不兼容时，程序在激活之前就会拒绝启动，不会占用授权。
2. 首次打开网页，先输入授权码激活。也可以通过环境变量 `AUTHGO_LICENSE` 预先提供，跳过网页输入。
3. 授权成功、核心就绪后，进入管理员初始化页面，设置管理员账户、密码和时区。
4. 登录后台，从插件市场安装可信插件，创建任务并填写设置。
5. 定时执行和凭据巡检默认都关闭，首页显示“定时执行未开启”。确认设置后在通用设置中按需手动开启。

设置中的“更换授权码”会保存新授权并重启核心。若 compose 中已设置 `AUTHGO_LICENSE`，也应同步修改或移除该环境变量，否则容器下次重启会再次使用环境变量中的授权码。

若出现“检测到不兼容的旧版本数据。本版本为全新程序，不支持沿用旧数据，请备份后清空数据目录再启动”，请先停止程序并完整备份原目录，再换用空目录。程序不会自动删除、导入或转换旧数据。

### 数据目录预检

启动器首先只读检查数据目录；检查通过后才读取授权、创建运行目录或启动核心。不兼容时直接退出，不提供激活入口。

预检使用 SQLite 的 `mode=ro&immutable=1`，只读取主库，不读取 WAL 内容，不创建、回放或合并日志，也不改动文件内容、名称或权限。非空 `-wal` / `-journal` 不再单独构成拒绝原因：

- 主库的产品身份、版本表和初始业务表确认属于本程序：放行，由核心正常打开数据库，交给 SQLite 完成日志恢复。
- 主库明确包含旧表、旧字段、不同产品身份或不支持的版本：拒绝启动，显示不兼容旧数据提示。
- 主库尚无足够结构确认来源，例如首次创建后从未 checkpoint：拒绝，但单独提示“数据库存在未完成的写入记录且无法确认来源，请确认是本程序的数据后再处理”，不把它判成旧数据。
- 其他进程持有数据库锁、检查期间文件变化或无法安全检查：仍拒绝启动。不存在主库却有遗留日志时也不初始化。

核心在初始结构事务及每次结构迁移提交后、管理员初始化和业务服务启动前，执行 `PRAGMA wal_checkpoint(TRUNCATE)`，并检查返回状态。失败会报错退出，不继续对外服务。因此已完成初始化、安装插件后的正常 WAL 可按本程序结构识别并恢复。

剩余窗口仅是**第一次创建数据库到首次结构 checkpoint 完成之前**遭遇强制结束；此时业务服务尚未启动，库中没有管理员、任务或插件数据。若能确认只是这次全新建库失败、从未完成管理员初始化或写入业务数据，可停止程序后清空该新建数据目录，重新开始。曾完成初始化、安装插件、写入业务数据或来源不清楚的数据不适用，应按下面步骤保留并恢复。

### 数据库来源无法确认时的处理

1. 停止所有使用该数据目录的程序或容器，完整备份整个目录，包括 `app.db`、存在的 `-wal` / `-shm` / `-journal`、`secret.key` 等；不要只复制主库，也不要删除日志。
2. 根据原部署镜像、挂载路径及备份记录确认来源。没有确认属于本程序的数据，不要尝试恢复后直接交给本程序，更不要手工补写产品身份或版本表来绕过检查。
3. 确认属于本程序后，先对**完整目录副本**操作：使用支持这份结构的原程序版本，或可信 SQLite 工具以正常可写方式打开副本的主库，让 SQLite 完成恢复和 checkpoint 后正常关闭。保留原始完整备份不动，不要手工删除副本日志来代替恢复。
4. 再让本程序检查处理后的副本；来源和结构确认通过后，才能在停机状态下使用恢复后的完整目录。检查仍不通过时，使用已知可用的完整备份；若不需要保留数据，可保留备份后改用空目录重新初始化。

主库已能确认属于本程序时，不需要上述人工处理；断电、强制结束容器或 OOM 留下的 WAL 会在通过预检后由核心正常恢复。

## 更新

后台“设置 → 关于与更新”显示当前版本、构建时间、最新版本、更新日志和维护期状态。程序启动后及每 6 小时检查一次，管理员也可手动检查；检查失败不影响授权状态。维护期已过时请按提示续费。

未启用网页更新时，在宿主机执行页面给出的镜像拉取命令，然后执行：

```sh
docker compose pull && docker compose up -d
```

网页更新能识别 `X.Y.Z` 和 `vX.Y.Z` 两种标签；平台版本号仍为不带前导 `v` 的语义化版本。程序严格校验平台给出的 `docker pull dingding229/sign-in:<标签>`，提取官方镜像引用后直接调用 Docker API，不执行命令字符串。

手动更新固定版本部署时，先把 Compose 文件中的镜像改为页面显示的目标版本，例如 `dingding229/sign-in:1.1.1`，再执行上述命令。否则 Compose 仍会使用旧的固定引用。

### 网页一键更新（可选）

仅当你自愿挂载 Docker 套接字，且程序能确认自身容器身份和持久化数据挂载时，才显示“立即更新”。在上面的 compose 服务中加入：

```yaml
services:
  app:
    image: dingding229/sign-in:latest
    ports:
      - "8000:8000"
    volumes:
      - ./data:/data
      - /var/run/docker.sock:/var/run/docker.sock
    restart: unless-stopped
    stop_grace_period: 35s
```

**风险：挂载后，能登录本程序后台的人等于拥有宿主机的最高权限。** Docker 套接字不是隔离沙箱；程序漏洞或管理员账户泄露也可能危及宿主机。不需要就不要挂载，用命令更新即可。只读挂载套接字也不能限制 Docker API 的写操作。

更新确认对话框在密码框上方显示当前版本 → 目标版本、将拉取的完整镜像引用、是否强制更新，以及自动备份目录 `data/backups/`。镜像必须先通过服务端校验；不合法时不显示“立即更新”，而是显示拒绝原因。对话框打开后目标或运行状态变化会阻止提交，服务端再次检查平台信息，发现目标变化则要求重新检查并确认。

触发更新时必须再次输入管理员密码。程序只接受授权平台给出的官方仓库版本，自动生成 `data/backups/` 业务备份，拉取镜像并固定 digest，再用新镜像启动一次性助手。助手给原容器 30 秒停止时间，按原始创建配置重建同名容器，验证新容器实际镜像 ID 匹配固定的 digest，最多等待 120 秒健康、核心就绪与目标版本检查。失败时尝试回滚原容器；后台显示成功或失败原因。

- **原镜像是 `dingding229/sign-in:latest` 或省略标签的 `dingding229/sign-in`**：更新会将本机的 `latest` 指向新镜像，容器保留原来的镜像引用字符串；回滚时将本机 `latest` 恢复为原容器的镜像 ID。这个本地标签在同一个 Docker Engine 内共享，也会影响用它新建的其他容器；不会推送到 Docker Hub。
- **原镜像是固定版本或其他引用（如 `signin-local:*`）**：不会改写原引用对应的本地标签，新容器使用此次更新的完整目标标签。成功后后台会显示原引用和目标引用。**请在下次执行 `docker compose up` 前，把 Compose 文件中的 `image:` 改为页面提示的目标引用，否则可能换回旧版本。** 网页不会修改宿主机上的 Compose 文件。

Compose v2 分别比较服务配置哈希 `com.docker.compose.config-hash` 和镜像 ID 标签 `com.docker.compose.image`。更新会保留原服务配置哈希，并将 Compose 镜像 ID 标签更新为新镜像的 ID。使用 `latest` 时，在 Compose 配置与本地标签未被其他操作改变的前提下，不会因网页更新触发重建；即使因其他配置变化重建，也能使用更新后的本地镜像。若 Compose 的拉取策略从仓库拉取并覆盖标签，则以实际拉取结果为准。对固定引用，未改 Compose 文件时，配置哈希可能仍匹配，但旧标签的镜像 ID 不匹配；改为目标引用后，`image:` 又会改变配置哈希，下次 `up` 可能按新引用再重建一次，这是预期行为。

重建期间页面短暂断开属于正常现象，请勿重复点击。结果保存在 `data/update/last-result.json`。若 Docker 故障、宿主机断电或助手被终止，自动回滚不能保证完成：保留原容器和备份，核对容器与结果文件后人工恢复。若结果一直停留在运行中，先确认并处理残留的更新助手、原容器和新容器，再备份并移走 `data/update/last-result.json` 后重启；没有确认助手停止前不要清除更新状态。不要在更新中并行执行 compose 重建、手动删容器或恢复备份。插件、业务数据在共享目录中，不因容器回滚自动恢复为备份版本；重大结构变更应先阅读更新日志。

## 插件更新

插件页与导航显示可更新数量。“全部更新”按顺序更新，单个失败不影响其他插件，结束后显示逐项汇总。周期检查只读取索引，不会自动安装。插件是可执行代码，可访问任务凭据，仅安装可信来源。

## 退出登录与设备会话

“退出登录”只让当前登录令牌失效，并立即断开该会话的事件流；其他浏览器或设备仍可使用。账户设置中的“退出所有设备”会撤销当前账户全部登录，包括当前设备。修改密码、忘记密码恢复和恢复业务备份同样会撤销全部旧会话。退出后即使重启程序，已撤销的令牌也不能重新使用。

## 忘记管理员密码

在宿主机交互式执行：

```sh
docker exec -it <容器> /app/launcher reset-admin
```

按提示输入两次新密码，输入时不回显；不接受命令行参数传密码。密码须为 10～72 字节且不含控制字符。成功后撤销所有已登录会话，并立即关闭这些会话的已有 SSE 连接，不等待心跳；重新登录即可。

该命令需要核心正在运行、授权有效且已完成管理员初始化。它使用数据目录内仅本地可访问的 `admin.sock`（权限 `0600`），由核心原子更新密码摘要并递增会话版本。无需把数据库或授权 SDK 引入启动器，也不通过公网暴露密码恢复接口。执行用户须为容器内核心所属用户或 root。

## 备份与恢复

后台可导出包含 `app.db`、`secret.key` 和校验清单的 ZIP 业务备份。仅接受本程序结构与格式一致的备份，恢复后需要重新登录。备份包含敏感凭据与解密密钥，应离线妥善保存。

业务备份不包含授权缓存、插件二进制、日志或自动备份历史。恢复后按页面提示重新安装或修复缺失插件。完整灾难恢复请在停止程序后备份整个数据目录，保留密钥及授权缓存。不得单独删除或替换 `secret.key`。

“设置 → 备份与恢复 → 更新前的自动备份”列出 `data/backups/` 中按程序规则命名的自动备份，显示文件名、创建时间、更新目标版本和大小，支持下载与确认删除。自动备份不会自动清理，请定期下载留存所需副本、手动删除不再需要的归档。更新进行中不能删除。

## 配置与运维

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| PORT | 8000 | 容器 HTTP 端口 |
| DATA_DIR | /data | 持久化数据目录 |
| WEB_DIR | /app/web | 静态页面目录 |
| AUTHGO_LICENSE | 空 | 可选，预先提供授权码 |
| CORS_ORIGINS | 空 | 分离前端时允许的精确来源，以逗号分隔 |

`/api/health` 用于容器健康检查，不需要登录。查看日志：`docker compose logs --tail=200 app`。反馈问题前应遮盖授权码、密码、Token、Cookie 和密钥，不要公开数据目录或备份文件。
